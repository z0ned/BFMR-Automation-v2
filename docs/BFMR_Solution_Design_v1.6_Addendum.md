# Solution design v1.6 - interactive email processing and browser ownership

10 October 2026. Read alongside the unchanged v1.5 PDF. This addendum records the user-approved browser lifetime and automatic quantity-one behavior, the normal skip behavior required for duplicate/full deals, and the email-link and diagnostic corrections made during interactive testing. It affects INT-002, OPS-002, FR-002, FR-004 and SEC-002. Engineering observations below are distinguished from confirmed requirements and live acceptance evidence.

The application opens one headed Chromium window at startup, before waiting for email. It owns one persistent browser context and reuses the same page for serial deal processing throughout its lifetime. Completion of an email, a reservation, an API check or a CAPTCHA does not close or replace that context. Cookies and session state remain available between tests. BFMR can request further CAPTCHAs; one challenge per application run cannot be guaranteed. Challenges remain manual.

Only application termination closes the browser. Ctrl+C and SIGTERM initiate browser cleanup. Unexpected process termination cannot guarantee graceful cleanup. A manually closed or crashed browser must stop processing, not silently create a replacement session or retry a reservation.

The interactive email test becomes a session: after API-confirmed success it waits for the next qualifying email using the same Gmail history cursor and browser. Remaining messages from a fetched history batch are retained by the iterator and processed serially. Quantity-one reservations proceed automatically after the existing preflight checks; there is no per-reservation approval prompt. A pre-action access challenge pauses for manual completion (PAGE-READY), and each post-action check still requires CHECK-API so the operator can finish any CAPTCHA. A failed test holds processing with the window open for inspection until the operator exits. It never retries an uncertain action.

An existing reserved row found during the preflight My Tracker check is a normal skip, regardless of quantity. Log SKIPPED, submit nothing, and continue waiting for the next qualifying email in the same browser. An unknown tracker result or an uncertain post-submit outcome still holds processing for inspection.

An explicit visible BFMR full/closed/no-slots message is also a normal skip. Detect it before requiring a catalog title, and recheck if the page changes during preflight or before the reservation click. A CLOSED_NO_SLOTS result proved before submission returns normally to the email listener. Missing titles/controls alone do not prove that a deal is full, and a full page after a possible submission does not bypass tracker reconciliation.

An explicit visible `Deal not found` message on a trusted deal-detail URL is also a normal unavailable-deal skip. Log that exact reason, submit nothing, and continue waiting for the next qualifying email. Do not click `Go Back To Deals Page`, choose another deal or retry the missing deal. A hidden message or a missing catalog title alone does not establish this outcome. If a reservation action may already have occurred, reconcile through My Tracker instead of using this message as proof of non-creation.

A redirect from a deal link to the generic `/deals` listing (including `?tag=all`) is an unresolved navigation/deal-identity mismatch, not proof of a full or unavailable deal. Pause before submission and retain the browser for inspection. Never select a replacement deal from the listing or automatically replay the email. This supersedes the temporary listing-as-unavailable skip introduced during diagnosis. The user subsequently demonstrated that the supplied tracked AirPods link opens its individual deal page manually; the automated browser's reason for reaching the listing remains unproved. Visible challenges, password forms, untrusted URLs and other page mismatches retain failure/manual-handling behavior. No post-click navigation outcome bypasses My Tracker reconciliation.

BFMR email links can use HTTPS `email.mail.buyformeretail.com/c/<token>` for products, navigation and unsubscribe actions. The observed token is base64url-encoded zlib data containing URL-encoded fields; its `l` field holds the destination. Node intake decodes this locally without visiting the tracker. Accept exactly one destination field and only an existing approved HTTPS BFMR deal-detail URL. Limit the encoded token to 8,192 characters and decompressed data to 16,384 bytes. Reject malformed, oversized or unsupported formats. Do not widen the browser navigation allowlist to include the tracking host. Navigation, image and unsubscribe links do not identify deals, and must not be followed during extraction.

Count distinct validated direct and decoded deal paths across the email. Repeated HTML/plain-text links and www aliases collapse; multiple distinct deal paths disqualify single-deal processing. Forwarded NEW DEAL subjects remain supported, including FULL RETAIL subjects without a retailer channel. Additional-slot and roundup exclusions remain in force. Skip logs distinguish subject/multiple-deal exclusions from missing or unsupported trusted deal links. Link decoding does not replace sender/provenance validation or prove browser/API account alignment.

Read the catalog title from the rendered individual deal page, rather than synthesizing it from an email subject or short-link token. The current reader waits up to 10 seconds for a unique visible semantic heading associated with the Payout Price / Retail Price section, excluding generic page and navigation labels. Missing or ambiguous titles still block reservation. This observed-layout implementation is not proof that every BFMR template has those labels. A listing route produces a navigation-specific diagnostic instead of being classified as a missing product title.

Navigation diagnostics record the requested BFMR origin/path and subsequent main-frame deal/listing origin/path changes. Omit query strings, tracking tokens, account text and unrelated route details. Failed title reads report heading counts/tags and price-label presence without logging heading text or raw pages. These diagnostics establish what the automated session visited; they do not by themselves explain a server/client redirect or justify a retry.

Verified example: the supplied AirPods tracking link decodes to `https://bfmr.com/deals/d-ikygz`, and a read-only HTTP request to that tracker returned 302 to the same destination. The actual AirPods email now qualifies as a single deal. The user's subsequent screenshot shows `Deal not found` at that exact deal-detail URL, explaining the absence of a product title in this case. The screenshot does not establish why BFMR considers the deal missing or prove a redirect to the listing; the earlier listing report is superseded as the explanation for this title failure. No reservation was made during these diagnostic checks.

This change does not certify the guided runner as the production durable intake service. It currently polls Gmail every 15 seconds and initializes its history cursor from the current mailbox profile before the startup reservation. Messages arriving during the startup reservation/CAPTCHA remain eligible. Emails already present before that baseline are excluded, including skipped mail from a previous test run; restarting does not replay them. This is a known test-runner limitation, not a change to the v1.5 durable catch-up requirement. Production cursor persistence/recovery, Pub/Sub intake and full account/deal/form identity validation remain separate work. Do not silently add an Inbox sweep or reset a production cursor to emulate this test behavior.

Acceptance evidence: `tests/browser_session.test.ts` covers one browser before intake, reuse across emails, failure retention and termination cleanup. `tests/bfmr_email_links.test.ts` covers tracked links, exclusions, repeated/multiple deals, malformed/oversized payloads and unsafe destinations using synthetic tokens. `tests/visible_deal_title.test.ts` covers title rendering, full messages, listing/login/challenge/unknown-page distinctions and sanitized diagnostics using synthetic intercepted Chromium pages. `tests/bfmr_url.test.ts` covers trusted detail/listing URL distinctions. Offline checks do not prove live multi-email/CAPTCHA reuse, all email/page templates, or end-to-end reservation correctness. See `IMPLEMENTATION_PLAN.md` for commands, results and outstanding live evidence.


## Live-test startup reservation — 10 October 2026

Matt clarified that this startup behavior applies to live reservation test scripts, rather than a production entry point. Every invocation of `npm run test-real-email` (including alias `test-real-email-e2e`) and `npm run test-bfmr-ipad-reservation` opens/reuses its dedicated Chromium context, navigates to `https://www.bfmr.com/deals`, clicks the visible In Stock filter, and considers the resulting deal links in displayed DOM order. This is an explicitly authorized exception to email-triggered selection. It does not change email navigation mismatch handling. Offline tests, sign-in/read-only helpers and the unfinished-reservation recovery command do not create an extra startup reservation.

Inspect the first candidate and perform the complete My Tracker duplicate check. If already reserved or explicitly full/closed/not found, skip it and inspect the next candidate. Submit quantity one through the existing website form for the first eligible candidate. Stop candidate selection after My Tracker confirms quantity one. An empty/all-skipped list logs that no eligible startup candidate was found and proceeds to the original test. Missing titles, unknown API reads and unexplained navigation mismatches still stop processing. The iPad test may therefore create a startup reservation plus its original target reservation; its original duplicate check remains active. All releases are manual.

Startup requires no terminal CHECK-API prompt. Check My Tracker automatically immediately after submission, then reread after 10 seconds and a further 20 seconds when confirmation is absent. Before delayed reads, detected access challenges wait up to five minutes for manual completion in Chromium. This is not a CAPTCHA bypass or a guarantee that BFMR will challenge at startup. A matching API-confirmed reservation completes startup even if a page challenge remains. Normal email processing retains its existing post-action CHECK-API interaction.

A missing reservation alone never authorizes another click. Only a definitive non-creation failure plus a complete negative tracker result permits submit ordinal two, after fresh page/duplicate checks; two failed ordinals exhaust that command. The current live adapter does not prove HTTP 500 non-creation, so unproved failures remain uncertain and require review. Unknown results, quantity conflicts and unresolved submissions stop the test with its browser retained.

Persist a SUBMITTING record before any possible startup click. The local live-test snapshot defaults to `~/.local/state/bfmr/startup-reservation.json`, with transition evidence in the adjacent `.events.jsonl` file; `BFMR_STARTUP_STATE_PATH` overrides the snapshot path. Files are created with owner-only permissions and synchronized to disk. An unresolved record is reconciled through My Tracker before any new startup selection; absence alone cannot clear it. A persisted proved-failure RETRY_PENDING record resumes at ordinal two. Keep the same state path across restarts and do not delete recovery evidence to force a retry. This local journal assumes the single browser/account owner; it is not the production PostgreSQL attempt store.

The email runner captures its initial Gmail history baseline before this flow, so emails arriving while the operator completes startup remain available to the listener. Pre-baseline messages are still excluded by the test-runner limitation above.

Offline evidence: `tests/startup_reservation.test.ts` covers ordering, duplicates/unavailability, API/manual-challenge confirmation, write-before-submit, uncertain outcomes, bounded retries, persisted recovery and browser lifecycle. Synthetic Chromium fixtures in `tests/visible_deal_title.test.ts` cover clicking In Stock and preserving the resulting link order. The actual BFMR filter markup, CAPTCHA lifecycle and live startup reservation have not yet been validated. Passing offline checks does not establish those provider contracts or production readiness.


Startup filter locator correction: the user supplied a visible In Stock filter alongside a timeout from the literal single-space text matcher. The screenshot does not establish its DOM text. The locator now accepts the exact two-word label with optional whitespace, a zero-width separator or a hyphen, accommodating adjacent styled spans that expose `InStock` while displaying a visual gap. It still requires a unique visible match and uses a normal Playwright click. Synthetic fixtures exercise ordinary text, adjacent spans, nonbreaking spaces and a hyphen, with a hidden duplicate ignored. Actual BFMR DOM confirmation remains pending the next live run.


## Superseding startup selection change — 10 October 2026

Matt removed the In Stock requirement after the locator still failed live. Startup now opens `/deals` and considers the visible deal links in their existing displayed order without finding or clicking any filter. Try the first deal, then advance past duplicates, explicitly unavailable deals and definitively failed reservations until a quantity-one reservation is confirmed through My Tracker or the displayed list is exhausted. Preserve the two-submit limit per deal for proved non-creation; after exhausting those ordinals, record EXHAUSTED and move to the next deal. An uncertain submission, unknown tracker read, authentication failure or quantity conflict still requires reconciliation/manual attention before another submission. This supersedes the In Stock selection and terminal exhaustion behavior described above. Startup remains manual-CAPTCHA/automatic-API verification with the same recovery journal and email baseline behavior.


Catalog title scoping correction: the startup iPhone page exposed three candidate headings (`h2`, `h5`) with both price labels. The supplied screenshot shows a catalog title, a subtitle and Additional Details. The previous reader let every heading inherit pricing context from a broad ancestor such as main/body. It now keeps candidates belonging to the tightest ancestor section containing both price labels, requires a single such section, and chooses its principal semantic heading level. Equal-level distinct titles or separate pricing sections remain ambiguous and block submission. No title is synthesized from the URL/email, and no first-heading fallback is used. Synthetic fixtures cover the pictured hierarchy; the screenshot does not establish exact live DOM nesting, so the live rerun remains necessary.


## Automatic confirmation and Telegram failures — 10 October 2026

Matt instructed that CAPTCHA completion should be assumed necessary only at startup, removed CHECK-API, and requested Telegram notification when reservations fail. This supersedes every retained post-action CHECK-API requirement above. The email and iPad test flows now proceed directly from the form action to read-only My Tracker confirmation, with an immediate read and up to twelve further reads at five-second intervals while the result is NOT_VISIBLE_YET. UNKNOWN or quantity conflicts end polling without another submission. The separate recovery helper also no longer requires CHECK-API; its explicit pre-action identity-review PAGE-READY step remains.

Startup still waits for manual CAPTCHA completion in Chromium and uses its existing automatic confirmation timings. No CAPTCHA bypass is added. After startup the email/iPad preflight treats a detected access challenge as an unexpected failure and alerts, without another terminal readiness prompt. Post-action confirmation remains automatic even if a challenge appears; API confirmation is authoritative. An unconfirmed possible submission remains uncertain and blocks additional work. BFMR may still issue challenges despite the startup-only operating assumption.

Live test entrypoints require TELEGRAM_BOT_TOKEN and TELEGRAM_CHAT_ID before opening the reservation flow. The server-side sender uses the official Telegram Bot API sendMessage method with a bounded request timeout and validates the HTTP response, ok flag and message identifier. It does not log token-bearing URLs, response bodies or underlying transport exceptions. Alerts contain the runner/deal context and direct the operator to My Tracker/the terminal; raw emails/account pages are not sent. Email/startup processing failures and iPad/recovery failures send an alert before the existing stop/inspection path. Proven startup submission failures also alert before retrying/advancing. Normal duplicate/unavailable skips do not generate email/startup failure alerts.

Alert-delivery failure is logged explicitly and does not authorize further reservation processing. These test-runner alerts are immediate sends, not the production durable PostgreSQL notification outbox; failed deliveries require operator intervention and are not automatically replayed across restarts. The existing production outbox requirement remains outstanding. No test alert or live Telegram message was sent during implementation. Synthetic injected-transport tests verify request construction, required configuration, delivery validation, redacted failures and preserving the original reservation failure; fake confirmation tests verify polling without a prompt or resubmission.

Provider reference: [Telegram sendMessage](https://core.telegram.org/bots/api#sendmessage).

## Amazon evaluation and startup cleanup — 10 October 2026

This later user instruction supersedes the no-evaluation/manual-release-only rule in v1.5 and earlier v1.6 handoffs for the following two cases:

- **Startup:** the quantity-one reservation exists only to trigger manual CAPTCHA. After My Tracker confirms success, cancel that exact reservation and verify release before the test proceeds. Do not evaluate its Amazon suppliers. This applies to both live test entrypoints that run startup; the Watch recovery helper remains excluded.
- **Incoming email:** after a newly submitted quantity-one reservation is confirmed, read its supplier entries. Keep it if Amazon is listed; otherwise cancel that exact reservation, confirm release, and resume email listening. Existing duplicate reservations are skipped without evaluation or cancellation. The dedicated iPad target and Watch recovery target are outside this email-only evaluation.

Implementation: `amazonEvaluation.ts` uses the documented read-only active-reservations endpoint and joins by exact `reserve_id` and API `deal_id` from the confirmed tracker row. It validates quantity and item/retailer-link structures, and matches the Amazon supplier label rather than searching email text, product titles, or retailer URLs. Any listed item with Amazon satisfies this first deal-level supplier check; no Amazon stock, price, seller, or per-component purchasing evaluation is added. Missing, malformed, conflicting, or unreadable supplier evidence is UNKNOWN: keep the reservation, stop, and alert through the existing Telegram failure path. It is never treated as Amazon absence.

Cancellation: one HTTPS POST to `https://api.bfmr.com/api/v2/my-tracker/reservation/cancel`, `Content-Type: application/x-www-form-urlencoded`, with a single `reserve_id[]` value. The user explicitly approved testing form encoding despite the inconsistent provider examples. Read the complete tracker before sending: require the exact reservation/deal IDs, Reserved status and quantity one. Do not cancel another deal, a purchased row, a duplicate row, or an existing preflight reservation. Redirects are rejected. Read the tracker immediately after the request and, while still reserved, after 2, 5 and 10 further seconds. HTTP success alone does not prove cancellation. Absence from a complete tracker collection or explicit canceled status confirms release; changed identities/statuses, incomplete reads and persistent active rows stop and alert. A timeout triggers read-only reconciliation, never an automatic repeat POST.

Recovery: `postReservation.ts` persists evaluation/cancellation intent before the write, then marks KEPT or CANCELLED only after the corresponding evidence. The owner-only local journal defaults to `~/.local/state/bfmr/post-reservation.json` (`BFMR_POST_RESERVATION_STATE_PATH` override). A pending cancellation after restart is reconciled read-only; if it is still active, operator review is required. Startup additionally records CLEANUP_PENDING with exact IDs and CLEANED after release. Pending work is resolved before a new startup attempt. Legacy completed startup entries lacking cleanup intent are not retrospectively canceled. These local files remain test recovery scaffolding, not PostgreSQL production durability or cross-process locks.

Live evidence: the user designated their sole active Fitbit Air Obsidian reservation for the encoding test. A complete tracker read verified the requested title, GA09509-US model and quantity one. One form-encoded cancellation request was sent; a subsequent complete tracker read confirmed it was no longer Reserved. No other reservation was canceled or created. This verifies that request shape for one real reservation; it does not establish all supplier response variants or end-to-end email evaluation. IDs and account response data are retained only in local runtime evidence, not this document.

Provider reference: [BFMR API documentation — Active Reservation List and Cancel Reserved](https://api.bfmr.com/). Use its documented HTTPS API host; the internal HTTP hostname in the sample is not used.

### Amazon sign-in resumption fix — 10 October 2026

The rehearsal waits in Chromium for manual Amazon sign-in/MFA/access challenges, with a ten-minute timeout. It no longer asks for terminal Enter after authentication. Once a challenge has been detected, a non-sign-in Amazon account label and absence of the challenge are required before automatic continuation. Login redirects to the homepage cause the intended cart/product page to be reopened; Add to cart is never repeated as login recovery. Unknown destinations or unresolved authentication stop the rehearsal. Intermediate address/payment choices still use the manual terminal confirmation. Final order submission remains prohibited.

Synthetic Chromium regression coverage includes cart and product login detours through MFA to the homepage, automatic continuation with no terminal callback, and timeout with no cart or order mutation.

### Product navigation before cart preflight — 10 October 2026

The Amazon rehearsal opens and validates the requested product URL before inspecting the active cart. A failed cart inspection returns to the requested product for inspection and reports the cart path, active container/row counts and whether an explicit empty-cart message was found. Unknown contents still prevent Add to cart. Empty-cart recognition accepts “Your cart is empty” in addition to the Amazon/Shopping variants. These are fixture-tested UI variants; the reported live cart layout has not been captured or verified.
